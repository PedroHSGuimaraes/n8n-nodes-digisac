# Project state

## Decisions

| ID | Decision | Rationale | Status | Date |
| --- | --- | --- | --- | --- |
| AD-001 | O pacote usa o `@n8n/node-cli` 0.55.5 para build e lint (`n8n-node build`, `n8n-node lint`, `n8n.strict: true`), sem gulp, sem config própria de ESLint e sem `dependencies` de runtime | A guideline de verificação do n8n manda usar a ferramenta `n8n-node`. Menu: "Qual escopo de atualização..." → "Migrar para node-cli" (Jev 0,96) | active | 2026-11-06 |
| AD-002 | Mudança de formato de parâmetro entra como versão leve do node (`version: [1, 2]`, `defaultVersion` 2, `@version` em `displayOptions`); a versão 1 mantém nome e tipo de todo parâmetro | Workflows salvos não podem quebrar. Menu: "Como tratar isso nos nodes já publicados?" → "Nova versão do node" (Jev 0,83) | active | 2026-11-06 |
| AD-003 | A entrega é branch, Pull Request, merge na `main` e tag `vX.Y.Z`, que publica no npm pelo `publish.yml` com provenance | Menu: "Como entregar e publicar as mudanças?" → "PR e publicar" | active | 2026-11-06 |
| AD-004 | A publicação usa `npx -y npm@12.2.2 stage publish --provenance --access public`; a versão fica em espera e o dono a aprova com 2FA na aba Staged Packages do npmjs.com | O token npm do dono é "Read and write (stage only)": com ele `npm publish` falha com `E_STAGE_REQUIRED`. `npm stage` só existe no npm 12 e o Node LTS do runner traz o npm 11. Decisão do dono, 06/11/2026 | active | 2026-11-06 |
| AD-005 | A devDependency `n8n-workflow` sobe de `^2.16.0` para `^2.46.5` e o lock fica em 2.46.x ou mais nova; o `peerDependencies` continua `*` | A tag `latest` do npm está parada em 2.16.0; a `stable` é 2.46.5, usada pelo n8n 2.46.6, e o audit cai de 5 para 3 CVEs altas. Decisão do dono, 06/11/2026 | active | 2026-11-06 |
| AD-006 | Só 8 tipos de ID viram Resource Locator com `From List` na versão 2: `contactId`, `serviceId`, `departmentId`, `userId`, `tagId`, `roleId`, `botId`, `ticketTopicId` | O node tem 298 operações e 32 tipos de ID no path; só esses 8 têm rota de listagem confirmada e uso alto (`contactId` aparece em 37 operações). Escolha do Jev: só os oito mais usados 0,52 (descartadas: todos com rota confirmada 0,43; só contactId e serviceId 0,05) | active | 2026-11-06 |
| AD-007 | Os outros 24 tipos de ID do path (ex.: `ticketId`, `messageId`, `cardsId`) viram Resource Locator só com o modo `id` na versão 2 | Mantém o mesmo formato de valor em todo ID do node e deixa a lista entrar depois sem trocar o tipo de novo. Escolha do Jev: Resource Locator só By ID 0,53 (descartada: manter string com dica 0,47) | active | 2026-11-06 |
| AD-008 | `generate:endpoints` e `generate:docs` saem do `build` e viram scripts manuais; `build` é só `n8n-node build`, e o catálogo gerado continua versionado | O gerador baixa a coleção Postman da rede; build que depende de rede quebra o CI e a publicação sem aviso. Escolha do Jev: fora do build 0,99 (descartada: manter no build 0,01) | active | 2026-11-06 |
| AD-009 | O README é escrito à mão no padrão completo do RD CRM; o `generate:docs` passa a gerar só `docs/api-calls.md` e a tabela de recursos entre marcadores do README | Hoje o `generate:docs` sobrescreve o README inteiro; o README completo não sobreviveria a uma regeneração. Escolha do Jev: README à mão 0,66 (descartada: gerador emite o README inteiro 0,34) | active | 2026-11-06 |
